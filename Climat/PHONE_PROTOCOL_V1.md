# MCU ↔ телефон: бинарный протокол v1

Новый контракт реализован по запросу пользователя 27.10.2026. Он не восстановлен из прежнего чата: прежнего байтового формата в предоставленных файлах не было. Реализация: phone_link.c (кадры и повторы), service_console.c (команды и общий backend), sensor_stage1.c (USART6).

## Транспорт

USART6: **9600 бод, 8N1**, TX PG14/D1, RX PG9/D0. USART3 остаётся текстовой консолью. Установленный BT05/v6.1 автоматически настраивается при старте как peripheral/slave; AT-чтением подтверждены service UUID FFE0 и characteristic UUID FFE1. Их фактические свойства write/notify и полный эфирный путь ещё нужно проверить. Подробности — `BLUETOOTH_BOOT.md`. После подключения телефон включает notify и отправляет HELLO. BLE-запись/уведомление может содержать любую часть кадра или несколько кадров; клиент собирает поток независимо от границ BLE-порций.

Один незавершённый запрос: **stop-and-wait**. Для новой операции — новый uint16 sequence; для повтора после потери ответа — прежний sequence и точно тот же кадр. Рекомендация: тайм-аут ответа 4 с, до двух повторов. При новом подключении начать с произвольного sequence и HELLO; при SEQUENCE выбрать другой номер. 65535 → 0 допустим. Следующую команду отправлять после подтверждённого ответа, особенно после SAVE.

Телеметрия запрашивается телефоном: GET_STATUS и GET_SENSORS примерно раз в секунду. Автоматической подписки/событий в v1 нет. Разрыв BLE не останавливает AUTO. MANUAL истекает по прежнему тайм-ауту; продлевают его только успешные MODE MANUAL и RELAY. Чтение, настройки и повтор уже выполненной команды срок не продлевают.

## Кадр

На проводе: **00 + COBS(raw) + 00**. Оба разделителя обязательны у отправителя; несколько 00 подряд допустимы. Максимум raw=71 байт, COBS-тело=72, полный кадр=74.

| Смещение raw | Тип/размер | Поле |
|---:|---|---|
| 0 | u8 | version=1 |
| 1 | u8 | opcode запроса 0x01…0x7F; ответ = opcode OR 0x80 |
| 2 | u16 | sequence |
| 4 | u8 | payload_length, 0…64 |
| 5 | N байт | payload |
| 5+N | u16 | CRC16 |

Все многобайтовые числа little-endian, знаковые — дополнительный код. CRC-16/CCITT-FALSE: poly=0x1021, init=0xFFFF, refin=false, refout=false, xorout=0; охватывает version…payload включительно. `123456789` → 0x29B1. CRC32 настроек Flash не является CRC UART.

Пауза между частями ≥500 мс отбрасывает накопленный кадр. После ошибки UART или переполнения очередь и частичный кадр отбрасываются до следующего 00. Длина/COBS/CRC проверяются до обращения к backend. Повреждённые кадры и кадры с установленным битом ответа молча игнорируются; клиент использует тайм-аут. На правильный CRC с неизвестной версией возвращается VERSION, версия ответа всегда 1. ASCII-сообщения модуля не являются командами терморегулятора.

## Ответы и повторы

Первый байт каждого payload ответа — status:

| Код | Имя | Смысл |
|---:|---|---|
| 0 | OK | Обработано; учитывать actual logical и ограничения |
| 1 | BAD_PAYLOAD | Неверная длина/аргумент |
| 2 | BAD_OP | Неизвестная команда |
| 3 | BAD_CONFIG | Проверка настроек не пройдена, RAM сохранена |
| 4 | DENIED | RELAY запрещён режимом, аварией или конфликтом |
| 5 | STORAGE_ERROR | Следующий байт: EMPTY=1, INVALID=2, IO_ERROR=3 |
| 6 | BUSY | Зарезервировано, пока не выдаётся |
| 7 | SEQUENCE | Последний sequence повторён с другим запросом |
| 8 | VERSION | Версия протокола не поддерживается |

Обычно ошибка содержит один status. DENIED для RELAY содержит полный ответ управления, STORAGE_ERROR содержит ещё код хранения. Ответ повторяет sequence и использует opcode запроса OR 0x80.

MCU кеширует **один последний полный запрос и его ответ**. Идентичный повтор возвращает побайтово тот же ответ, не выполняет команду снова и не продлевает MANUAL. Другая команда с тем же последним sequence получает SEQUENCE без замены кеша. Новый sequence заменяет кеш. После reset/потери питания/PHONE TEST кеш отсутствует; старые запросы после более новых не защищены от повторного исполнения. Клиент не выполняет параллельные запросы и не повторяет старую команду после перехода к следующей. Для нового чтения статуса нужен новый sequence, иначе вернётся кешированный снимок.

## Команды

| Opcode | Команда | Payload запроса | Успешный ответ |
|---|---|---|---|
| 0x01 | HELLO | Пусто | 9 байт |
| 0x02 | GET_STATUS | Пусто | 23 байта |
| 0x03 | GET_SENSORS | Пусто | 51 байт |
| 0x04 | GET_CONFIG | Пусто | 34 байта |
| 0x05 | SET_CONFIG | 23 байта | status |
| 0x06 | SAVE | Пусто | status, unchanged:u8 |
| 0x07 | LOAD | Пусто | status |
| 0x08 | DEFAULT | Пусто | status |
| 0x09 | MODE | mode:u8, 0=AUTO / 1=MANUAL | 6 байт управления |
| 0x0A | RELAY | relay:u8 (1…4), on:u8 (0/1) | 6 байт управления |
| 0x0B | GET_STORAGE | Пусто | status, flash_state:u8, ram_matches:u8 |
| 0x0C | GET_DEVICE_NAME | Пусто | status, name:3 байта |
| 0x0D | SET_DEVICE_NAME | name:ровно 3 байта | status |

SET_CONFIG атомарно проверяет весь набор и применяет его только в RAM, сбрасывает запросы и переводит в AUTO. LOAD и DEFAULT также переходят в AUTO. LOAD при ошибке сохраняет RAM. DEFAULT восстанавливает принятый тестовый профиль в RAM. Для постоянного хранения требуется отдельный SAVE; ответ OK подтверждает чтение/CRC после записи. unchanged=1 — совпадение без стирания. Во время SAVE UART временно приостанавливается. Одна страница без копии и ранее принятый риск потери при сбое питания сохранены.

Ответ управления: `[status, mode, requested_mask, logical_mask, fault, physical_locked]`. Биты 0…3 маски — K1…K4. OK означает принятый запрос; logical может отставать из-за минимумов ON/OFF или включённой противоположной группы. Авария двух датчиков немедленно задаёт K1/K2 OFF, K3 ON, K4 OFF. С 28.10.2026 пользователь разрешил физические реле F767 с включением HIGH: physical_locked=0. У предварительного F030 physical_locked=1, выходы LOW. Формат v1 не менялся; клиент читает признак из устройства.

Последнее уточнение 28.10.2026: в **MANUAL ON, OFF и повторное ON выполняются сразу**, MIN_ON/MIN_OFF не применяются. В AUTO действуют оба минимума. Взаимная блокировка нагрева/охлаждения сохраняется; при аварии ручная команда, отменяющая обязательную маску K3 ON, отклоняется. Длины/статусы ответов не менялись. Константы минимальных времён из GET_CONFIG относятся к AUTO; приложение не должно показывать их как ожидание в MANUAL.

### HELLO (смещения payload)

0=status; 1=protocol_version (1); 2=max_payload (64); 3=window_seconds (5); 4=forecast_seconds (30); 5=capabilities (бит0 physical_locked, бит1 Flash backend, бит2 команды трёхбайтового имени; F767=6, заблокированный F030=7); 6=Flash format version (3); 7=sensor_slots (2); 8=relay_count (4). Неизвестные биты capabilities клиент игнорирует.

### GET_STATUS

| Смещение payload | Тип | Значение |
|---:|---|---|
| 0 | u8 | status |
| 1 | u32 | uptime_ms |
| 5 | u8 | mode |
| 6 | u8 | источник: 0 нет достоверного выбранного, 1 S1, 2 S2 |
| 7 | u8 | flags: бит0 fault, бит1 sampled, бит2 physical_locked, бит3 AUTO настроен, бит4 прогноз активен |
| 8 | u8 | requested_mask |
| 9 | u8 | logical_mask |
| 10 | u8 | physical_mask, прочитанные GPIO ODR K1..K4; у заблокированной платы 0. Это уровни выходных регистров, не обратная связь контактов реле |
| 11 | u32 | manual_remaining_ms |
| 15 | u32 | sample_age_ms; 0xFFFFFFFF до первого результата |
| 19 | i32 | effective_temperature_milli_C для AUTO |

### GET_SENSORS

status:u8, uptime_ms:u32, затем S1 и S2 — два блока по 23 байта. Смещения внутри блока:

| Смещение | Тип | Значение |
|---:|---|---|
| 0 | u8 | flags: бит0 assigned, бит1 valid, бит2 trend_valid |
| 1 | 8 байт | ROM в порядке Dallas, до назначения нули |
| 9 | i16 | Измеренная температура, 1/16 °C |
| 11 | i32 | Производная, 0,001 °C/мин |
| 15 | i32 | Прогноз, 0,001 °C |
| 19 | u32 | error_count |

При сброшенном valid/trend_valid соответствующие числа могут быть старыми и не используются.

### GET_CONFIG / SET_CONFIG

GET_CONFIG: status, затем блок 23 байта как в SET_CONFIG и readonly-поля. Смещения внутри блока SET_CONFIG (без status):

| Смещение | Тип | Значение |
|---:|---|---|
| 0 | 9 × i16 | target, h1on, h1off, h2on, h2off, c1on, c1off, c2on, c2off; 1/16 °C |
| 18 | u8 | FAIL_COUNT, 0=не настроено, иначе 1…255 |
| 19 | u8 | RECOVER_COUNT, 0=не настроено, иначе 1…255 |
| 20 | u8 | alternate, 0/1 |
| 21 | u16 | MANUAL_TIMEOUT, 1…3600 с |

Readonly-поля GET_CONFIG на смещениях payload: 24=window_seconds:u16 (5), 26=forecast_seconds:u16 (30), 28=min_temperature:i16 (168 = 10,5 °C), 30=heater_min_seconds:u16 (30), 32=fan_min_seconds:u16 (60). Передача readonly-полей в SET_CONFIG отклоняется по длине. Температурный валидатор общий с консолью: вложенные ступени, гистерезис, нейтральная зона. GET_STORAGE flash_state: VALID=0, EMPTY=1, INVALID=2, IO_ERROR=3. ram_matches проверяет фактические байты Flash и текущий формат RAM.

### Трёхбайтовое имя устройства

Имя — три байта без терминатора и без ограничения значений. Для короткого читаемого имени можно использовать ASCII, например A01 = 41 30 31. 00 00 00 означает «не назначено». Уникальность среди устройств назначает пользователь или приложение; MCU не проверяет чужие имена. При старте MCU поле используется для имени Bluetooth CLM-XXXXXX: A01 даёт CLM-413031. После SET_DEVICE_NAME требуется SAVE и перезапуск MCU для переноса имени в модуль; само редактирование не прерывает соединение.

GET_DEVICE_NAME возвращает четыре байта `[status,name0,name1,name2]`. SET_DEVICE_NAME принимает ровно три, изменяет RAM без переключения режима и без продления MANUAL; для постоянного хранения нужен SAVE. Длина SET_CONFIG по-прежнему 23 байта: эта команда сохраняет текущее имя. LOAD восстанавливает имя из Flash, DEFAULT очищает его в RAM. Валидные записи Flash v1/v2 читаются с пустым именем; запись нового формата v3 — только по SAVE.

## Эталон и проверка до готовности телефона

`tests/phone_codec.ps1` — независимый reference codec; `tests/phone_vectors.json` — готовые hex-векторы для тестов Kotlin. Это новый публичный контракт; будущий codec Android должен использовать те же поля и единицы.

Через USART3 доступны PHONE STATUS, PHONE TEST ON, PHONE HEX <hex кадра или части>, PHONE TEST OFF. TEST ON использует тот же парсер и рабочий backend, ответы выводятся как PHONE TX <hex>; физический UART6 в этом режиме игнорируется. Это настоящие операции с RAM/Flash, поэтому после проверки восстановить настройки и выключить TEST. При переключении TEST очищается кеш и парсер. Строка консоли — до 95 символов; большие кадры разбивать без паузы ≥500 мс. После reset TEST OFF, автоматический приём USART6 включён по прерываниям. Команды BT AT/ATLF остаются только явной диагностикой модуля и временно приостанавливают бинарный приём.

На NUCLEO прошли SELFTEST, AUTO_SELFTEST, SETTINGS_SELFTEST, TREND_SELFTEST, PHONE_SELFTEST. Проверены длины 0…64, CRC/COBS, каждый вариант дробления, переполнение, обрыв, повтор/конфликт sequence и wrap времени. Независимый клиент через USB передал бинарные пакеты в MCU: чтение данных, атомарный отказ SET, MODE/RELAY с конфликтом, SAVE с повтором, LOAD/DEFAULT, неизвестные opcode/версия, неверный CRC и тайм-аут части кадра. Исходные настройки восстановлены во Flash. Это испытание алгоритма/backend на MCU; полный эфирный путь телефон ↔ BLE ↔ USART6 ещё не испытан.

Эталонный HELLO из JSON дополнительно отправлен на MCU: ответ побайтово совпал с hello_locked_reply. Финальное состояние: PHONE TEST OFF, AUTO, STREAM ON, Flash VALID и ram_matches=1, COM3 освобождён. Переносимые модули скомпилированы для Cortex-M0 с -Wall -Wextra -Werror. Диагностический Release: text=33032, data=124, bss=3428 байт (включая резерв стека 2048); он пока не укладывается в лимит Flash F030. Фактическая максимальная глубина стека конечной сборки не измерена. Артефакты и логи — phone-protocol-release в копии результатов.
